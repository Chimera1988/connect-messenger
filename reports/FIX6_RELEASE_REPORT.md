## Причина поломки и исправления P0

В PWA и native сравнивался серверный answer SDP с текущим `localDescription.sdp`. WebRTC дописывает ICE-кандидаты в localDescription после отправки ответа. Поэтому собственный выигравший ответ ошибочно считался ответом другого устройства и локальное соединение закрывалось. Старый обработчик PWA воспроизвёл cleanup при добавлении одного ICE-кандидата с прежними ICE/DTLS-параметрами. Реальный тестовый WebRTC подтвердил рост SDP с 0 до 4 кандидатов.

Оба клиента теперь фиксируют неизменяемый отправленный answer до RPC. При проигрыше ответа второе устройство отправляет безопасный decline, который существующая серверная защита игнорирует для уже активного разговора другого устройства. Устаревшее завершение не переносится на следующий callId.

Также исправлены потеря ICE при ошибке вставки и длинные очереди: подтверждаемая очередь с повтором, курсорная догрузка ICE; native отправляет кандидаты ограниченными пачками. PWA ограничивает зависшее соединение и переподключение. Push повторяется ограниченно. Зависшая web-подписка больше не блокирует FCM: до четырёх независимых отправок с приоритетом Android, timeout web push 6 с и до двух попыток на устройство. Некорректный VAPID не прерывает Android-доставку. Сервер сообщает HTTP 503 при отсутствии настроенного транспорта вместо тихого успеха. Существующие ringing/accepted/ended и сигнатуры RPC совместимы с PWA/Android. ACTIVE не включается только по нажатию «Ответить».

Диагностика ограничена ID вызова/устройства, этапом, кодом и состоянием. SDP, ICE-адреса, токены, имена и аудио в диагностический журнал не записываются. Звуки, native экран, микрофон и фоновые вызовы остаются у Android; WebView не получает их жизненный цикл. Код/ресурсы Telegram не копировались.

Это доказанная причина части обрывов, а не доказательство устранения любой причины недоставки. Серверные журналы до исправления показывали 36 start, 4 answer и 38 finish RPC с HTTP 200 за доступный период; 7 ранних failed не имели answer/ICE. Рабочая конфигурация TURN и Firebase Admin недоступна для проверки. STUN не гарантирует соединение через мобильный/symmetric NAT.

## Сервер

Проверено фактическое применение `connect_call_response_owner_v1`, версия 20261110105648; Realtime опубликован для calls/ICE. Права call RPC не менялись.

Добавлена и применена **только** миграция `20261110151449_connect_fix6_history_barrier.sql` (`connect_fix6_history_barrier`). До/после — 310 сообщений, из них 72 ранее soft-deleted. Созданы 72 события удаления без содержимого, RPC `connect_deleted_since`, индексы курсора/страниц, RLS участников, запрет повторного использования удалённых UUID. Добавлена ограничительная SELECT-политика calls: старая permissive visibility-политика не должна через OR раскрывать чужой signaling. Содержимое сообщений/файлы не очищались и не переписывались. Старые широкие E2EE/purge-миграции не запускались.

События нужны офлайн-устройствам для недопущения возврата удалённых сообщений. Обычная очистка кеша не удаляет эти барьеры. Управляемое повторение/откат и оставшиеся advisory notices описаны в `supabase/FIX6-OPERATIONS.md`; схема отката сохраняет журнал, защиту ID и call fence. Новые security/performance notices не скрывались отключением проверок. Уведомления advisors о существующих SECURITY DEFINER RPC и настройках Auth перечислены там с официальными ссылками.

Для развёртывания PWA API на существующем HTTPS proxy нужны действующие Firebase Admin и coturn/TURN переменные. Их значения не извлекались и не помещались в APK. YAML сохраняет SQL в репозитории и не запускает все старые pending-миграции на случайном сервере.

## Что остаётся неподтверждённым

Нет ADB-устройств и /dev/kvm; физическая установка/запуск APK, Android 10/новые версии и iPhone Safari/PWA не испытаны. Не подтверждены четыре реальные пары PWA/Android, двусторонний микрофонный звук, Wi-Fi/LTE/смена сети/TURN, FCM при убитом интерфейсе, экран блокировки, системная мелодия/свой файл, вибромотор, DND, Bluetooth/SCO и системная громкость. Не выполнены реальные login/invite/hidden-user/медиа/музыка с пользовательскими аккаунтами: synthetic UI не подменяет эти проверки. Не создано тестовых звонков или сообщений в рабочих аккаунтах.

Локальный RTC-тест использует отдельный тестовый Linux WebRTC, поскольку управляемый Chromium запрещает захват микрофона и direct UDP. Политики браузера не обходились. Зависимость только dev/test, в APK не входит.

Для аппаратной приёмки: два аккаунта на PWA/Android; проверить каждое направление, ответ/отказ/таймаут/отбой обеих сторон, повтор после ошибки; затем непрочитанное сообщение → входящий на блокировке → отмена вызывающим → отсутствие рингтона/вибрации/notification → следующий звонок; повторить с двумя устройствами принимающего аккаунта и на разных сетях. Принятый разговор другого устройства должен продолжиться при позднем decline проигравшего. Эти сценарии не отмечены пройденными.
