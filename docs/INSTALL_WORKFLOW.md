# Самостоятельный workflow исправлений

Файл доставки: `connect-architecture-remediation.yml`. Добавьте его в исходный репозиторий по точному пути `.github/workflows/connect-architecture-remediation.yml`, затем запустите через Actions → Run workflow. До этого не меняйте другие исходники: пакет рассчитан на `b400ecc2057848d00998b04db813bcb2440ff79e`. Единственное разрешённое изменение HEAD перед установкой — сам этот YAML.

`prepare` проверяет SHA-256 встроенного payload и каждого файла, исходную версию, затем устанавливает изменения в checkout runner. Повторная установка принимает только точное исходное/целевое содержимое. Неизвестный diff останавливается до записи. Запускаются типы, архитектура, Deno, все обнаруженные регрессии, SQL, реальный локальный WebRTC, production build и тест PWA в Chromium. Только успешная проверка позволяет создать отдельную ветку/PR; main не переписывается, force-push и автоматического merge нет.

Для PR с изменениями `.github/workflows` нужен secret `CONNECT_REMEDIATION_TOKEN` с разрешениями репозитория **Contents, Pull requests, Workflows: write**. Ограниченный `GITHUB_TOKEN` обычно не имеет права менять workflow и не запускает повторный CI от собственных событий. Для проверки без публикации выберите `publish_review_branch=false`: GitHub token не нужен сверх обычного чтения checkout, результат доступен как artifact.

Режим `backend` описан в [BACKEND.md](BACKEND.md). Он отдельно требует подтверждения, ID резервной копии и environment secrets. В обычном `prepare` рабочая БД и Edge deployments не изменяются. До применения backend не объединяйте PWA PR: новая версия использует новые RPC.

Если появился `SOURCE_DRIFT`, не отключайте guard: пакет нужно пересобрать/проверить относительно новой main. Если существующая release-ветка имеет другой diff, публикация остановится; она не будет перезаписана.
