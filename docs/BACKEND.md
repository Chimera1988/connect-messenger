# Backend: восстановление, проверка и отдельное применение

Рабочая БД в ходе подготовки не изменялась. Источник — схема и определения функций проекта `tpwkmoxxzjfdsqsomhhr`, прочитанные 18 ноября 2026; пользовательские таблицы не выгружались.

## Два разных пути

Для пустого **изолированного Supabase** нужны штатные schemas Auth/Storage/Vault/extensions/net и publication `supabase_realtime`. Сначала применяется `supabase/baseline/connect.sql`, затем только пять upgrades `supabase/migrations/20261118*.sql` по порядку. Baseline — наблюдавшаяся схема до исправлений, включая старое поведение удаления; не используйте её отдельно. Старые миграции 20261110/предыдущих исправлений уже отражены в snapshot: повторно выполнять всю историческую папку поверх baseline нельзя.

Для существующего Connect baseline **не применяется**. Только `supabase/preflight.sql`, затем пять upgrades. Preflight сверяет 23 определения функций с наблюдавшимся источником или проверенной целевой версией. Неизвестное состояние останавливается с `BACKEND_SOURCE_DRIFT`; не обходите проверку и не выполняйте `db push --include-all` для неполной старой истории миграций.

## Порядок выпуска

1. Запустить standalone workflow в режиме `prepare`; получить проверенную ветку/PR, изучить diff и отчёт.
2. Проверить upgrades на отдельном Supabase, в том числе Auth delete и Storage API. Сделать резервную копию/restore point рабочей БД.
3. Настроить GitHub environment `connect-backend` и secrets `CONNECT_DATABASE_URL`, `SUPABASE_ACCESS_TOKEN`. URI должен вести на этот проект, использовать `sslmode=require` или более строгий TLS; подходят direct host или session pooler с пользователем `postgres.tpwkmoxxzjfdsqsomhhr`.
4. В исходном standalone workflow выбрать `backend`, ввести `APPLY_REVIEWED_CONNECT_BACKEND` и ID уже выполненной резервной копии. Сначала снова выполняются проверки исходников/тесты/build. Затем применяются upgrades и развёртываются четыре активные функции. После объединения PR тот же этап доступен как `Connect backend apply (manual)`.
5. Проверить вход/отзыв сессии, отправку/чтение, push, звонок двух устройств, удаление тестового аккаунта и медиа. Затем объединять PR и выпускать PWA обычным способом.

SQL upgrades выполняются отдельными транзакциями. Это позволяет безопасно повторить частично завершившийся выпуск: preflight принимает уже установленные целевые определения. Ошибка останавливает дальнейшие шаги; автоматического удаления таблиц или отката данных нет. Возврат старого PWA совместим с добавленными столбцами; для семантики удаления аккаунта и GC требуется отдельный план восстановления, нельзя слепо откатывать только один триггер.

## Контракты

- Service routes и прямой доступ к данным проверяют существующую активную Auth session и блокировку профиля. SECURITY DEFINER RPC звонков проверяют тот же контракт.
- Push endpoint имеет одного владельца, привязан к session ID. Старые регистрации без session ID не получают приватный push до повторной регистрации при открытии клиента; сессию другого устройства использовать нельзя. Новая регистрация заменяет владельца атомарно.
- Realtime публикация дополнена `conversation_user_state`, `profiles`, `conversations`. Отсутствующая publication блокирует применимость.
- GC: `connect_gc_prepare` → Storage remove → `connect_gc_ack`. Путь после retirement повторно не используется; новый upload получает новый UUID. Незавершённая загрузка защищается lease на 24 часа.
- Call lease применяется только когда обе стороны участвуют в новом протоколе и обе перестали продлевать lease. Работающий peer защищает приостановленный браузер; активный звонок делает редкий heartbeat и в фоне. Старые/native клиенты сохраняют прежний совместимый fallback; отдельный cron не создаётся этим пакетом.
- Удаление Auth обезличивает профиль; peer history и используемые ею файлы сохраняются. До подтверждения Auth delete приложение не сообщает об успехе.
- Gateway `verify_jwt` сохранён по фактическому inventory. GC использует приватный токен; конвертер проверяет пользователя/сессию и лимит. Секреты в исходники не включены.

В `ops/legacy-edge` лежат справочные снимки трёх maintenance endpoints. Два старых backfill endpoint остаются в проекте, но не вызываются и не развёртываются этим пакетом. Их удаление допускается только после отдельной проверки потребности в восстановлении; текущие пользовательские функции не зависят от Neon.

## Проверка

`npm ci`, установка закреплённого Playwright Chromium, `npm run typecheck`, `npm run check:architecture`, `npm test`, `npm run check:edge`, `npm run build`, `npm run test:e2e`. Для Edge используется Deno 2.5.6 с `supabase/deno.lock`. SQL тестируется настоящим Postgres-движком PGlite с синтетическими Auth/Storage границами; это не подмена испытаний GoTrue/Storage на staging.
