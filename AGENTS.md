Приоритет
Не повторять уже известные ошибки CI. Прежде чем разрабатывать код, workflow (.yml / .yaml), Android-сборку или исправление, прочитать этот документ и сверить актуальную main с последними успешными и неуспешными GitHub Actions. Изменения исходного кода требуют тестов; не выдавать «готово» без подтверждения.
Этот документ — инструкция для AI-агентов. GitHub Actions не применяет его правила автоматически: каждое новое workflow обязано реально содержать проверки.
Проверки перед написанием YAML или патча
	1.	Получить последнюю версию main и прочитать дерево файлов, затрагиваемые исходники и тесты, package.json, package-lock.json, tsconfig.json и существующие workflows. Не использовать фрагменты старых диалогов вместо содержимого текущего репозитория.
	2.	Найти актуальный успешный CI и релевантные упавшие запуски. Для каждого падения анализировать первое первопричинное сообщение, а не только Process completed with exit code 1.
	3.	Убедиться, что все целевые файлы реально существуют и содержат ожидаемые функции/импорты. Новые файлы создавать осознанно; не предполагать существование components/ConnectTranscript.tsx и других прежних путей.
	4.	Перед точечной заменой проверить уникальность текстового якоря и ожидаемое состояние файла. Защита от SOURCE_DRIFT обязательна; не удалять её и не заменять на || true.
	5.	Патч должен быть идемпотентен: повторное применение не дублирует изменения. Если виден маркер уже применённого обновления — подтвердить полное соответствие итогового состояния, а не пропускать проверку вслепую.
	6.	До модификаций определить область: PWA и Android — не одно и то же. При PWA-only задаче не трогать Android и наоборот. Не смешивать UI-изменение с привилегированными миграциями Supabase без прямой необходимости.
	7.	Для изменения поведения следовать TDD: воспроизвести сбой проверкой, исправить, запустить целевые тесты и полный регрессионный набор. Не подгонять тест под неправильное поведение.
Проверенная конфигурация PWA на дату аудита
	●	Рабочий репозиторий: Chimera1988/connect-messenger; основная ветка: main.
	●	runs-on: ubuntu-24.04 — не ubuntu-latest для текущего Playwright. На Ubuntu 26.04 установленный Playwright 1.58.2 ранее не смог подготовить Chromium. При обновлении Playwright проверять совместимость заново.
	●	Node.js: 22 — использовался в успешной проверке; перед изменением сверить актуальные engines/workflow.
	●	Перед actions/setup-node@v4 с cache: npm нужно сделать checkout и подтвердить наличие непустого package-lock.json. Если lock отсутствует, решить это отдельно, а не повторять провал cache step.
	●	После npm ci --no-audit --no-fund выполнить npx playwright-core install --with-deps chromium (использовать ту же версию, что и установленный в проекте playwright-core); затем проверить наличие require('playwright-core').chromium.executablePath().
	●	Не использовать безверсионный npx playwright install: он уже установил браузер для Playwright 1.65, пока тесты требовали playwright-core@1.58.2.
	●	Chromium должен устанавливаться до npm test — тесты кеша/медиа запускают реальный браузер.
	●	Внешний DNS/apt-сбой — повод к ограниченному повтору установки, а не к переписыванию источников. При повторном сбое остановиться с ясным сообщением.
Минимальный фрагмент подготовки CI
jobs:
  verify:
    runs-on: ubuntu-24.04
    timeout-minutes: 45
    steps:
      - uses: actions/checkout@v4
        with:
          ref: main
          fetch-depth: 0
      - name: Require npm lockfile
        run: test -s package-lock.json
      - uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: npm
      - run: npm ci --no-audit --no-fund
      - name: Install matching Chromium
        run: npx playwright-core install --with-deps chromium
      - name: Check browser executable
        run: node -e "const fs=require('fs');const p=require('playwright-core').chromium.executablePath();if(!fs.existsSync(p))process.exit(1)"
      # Применить патч в рабочей копии (если это workflow обновления).
      - run: git diff --check
      - run: npm run typecheck
      - run: npm test
      # npm run build — при наличии обязательных build-переменных.
      # Commit/push допустим только ПОСЛЕ всех проверок.
Пример — не заменяет целевые тесты и сборку конкретной задачи. Выбор runner и версий зависит от актуальных зависимостей, а не от постоянной фиксации старых значений.
Запреты и правила фиксации результата
	●	Не коммитить в main, если git diff --check, npm run typecheck, полный npm test, необходимые специфические тесты или применимая production build не прошли. Не отключать и не пропускать сломавшиеся тесты ради зелёной галочки.
	●	Не исправлять функциональную ошибку кеша (blob:), WebRTC/ICE или JSX простым изменением YAML: сначала определить, что реально неверно — код, тест или окружение.
	●	Не считать TS1005, TS1381, TS2304, TS2339, TS2322 одной ошибкой. Проверять синтаксис, область видимости, типы Web API, PromiseLike и корректную передачу BufferSource.
	●	Не вставлять одинаковые блоки и не создавать конкурирующие workflows без необходимости. Перед созданием очередного FIX2/FIX3 выяснить причину прежнего падения по его логу.
	●	Для пишущих workflows использовать минимально необходимые permissions (например, contents: write только если нужен push), защиту конкуренции, обычный push без --force, коммит только после всех проверок. Проверять, что итоговый YAML не пуст и содержит работающий job.
	●	Нельзя скрывать сетевые сбои и ошибки миграции Supabase. Привилегированная миграция требует явной проверки подключения, секреты в логи не выводить. Без надёжной авторизации — остановиться.
	●	Временные входные файлы, содержимое секретов, SDP, токены и пользовательские данные в диагностике не публиковать.
	●	Если GitHub выдаёт ошибку прав 403, не заявлять, что файл был загружен или commit выполнен. Предоставить корректный файл и честно указать, что пользователь должен добавить его вручную.
	●	После успеха CI не утверждать, что функции, зависящие от iOS/Android/оборудования, протестированы физически: требуется проверка на реальном устройстве.
Порядок завершения задачи
	1.	Проверка исходного состояния и прошлых ошибок.
	2.	Функциональный тест, воспроизводящий дефект (где применимо).
	3.	Минимальное изменение без посторонних правок.
	4.	Проверки структуры YAML, существования файлов и ожидаемых якорей.
	5.	git diff --check, typecheck, целевые тесты, полный npm test, затем применимая сборка.
	6.	Commit/push или PR только после проверок; при проблемах с правами сообщить об ограничении.
	7.	Сохранить run URL, фактическую причину и меру профилактики для новых ошибок.
